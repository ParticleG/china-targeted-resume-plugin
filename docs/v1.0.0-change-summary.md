# v1.0.0 Change Summary

## Overview

Version 1.0.0 turns the project into a more usable experienced-hire workflow with adaptive resume variants, stricter role relevance, auditable experience-duration diagnostics, a guided standalone CLI, and a validated downstream capability-growth roadmap boundary.

The release preserves the core invariants:

- The career knowledge base remains read-only.
- Generated artifacts stay outside the source root.
- Private directories use `0700`; private files use `0600`.
- Company research, plans, study-only knowledge, stale material, and unsupported claims never become candidate evidence.
- Contribution verbs, metric scope, qualifiers, source hashes, spans, evidence IDs, claim IDs, and provenance remain intact.
- Resume templates remain semantic and single-column.
- A learning plan never changes current evidence or match state.

## Adaptive Resume Variants

The request-level template strategy now accepts:

- `adaptive` — the new default;
- `ats-simple`;
- `human-readable`.

`adaptive` resolves per variant:

| Variant | Concrete template | Purpose |
| --- | --- | --- |
| `resume-recruiter-1p` | `ats-simple` | Recruiter scan and ATS ingestion |
| `resume-technical-2p` | `human-readable` | Hiring-manager and technical review |
| `technical-profile-3p` | `human-readable` | Optional extended technical history |

Each variant retains its own evidence budget, density, page target, semantic compaction, audit, PDF inspection, and underfill state. `resume-variants.json` now records the resolved concrete template for every variant.

Multi-column rendering remains intentionally unsupported. Page-count variants differ through content selection, density, typography, and reader emphasis without introducing ambiguous ATS reading order.

## Experienced-Hire Writing and Relevance

A new experienced-hire writing contract lives at:

- `skills/china-targeted-resume/references/social-hire-writing.md`

It defines evidence-safe use of contribution verbs such as `led`, `owned`, `designed`, `implemented`, `drove`, `coordinated`, and `contributed`. It also covers:

- problem, decision, scope, action, and result structure;
- mixed recruiter and hiring-manager readability;
- metric baselines, time windows, environments, and populations;
- team-versus-personal attribution;
- conventional terms such as QPS, P99, SLO, RTO/RPO, GMV, and A/B test;
- replacement of low-information jargon with concrete objects, actions, boundaries, and outcomes.

For `targeted_application`, visible resume selection now behaves as follows:

- If requirement mappings exist, unmapped evidence is excluded.
- Only `已有直接证据` and `可迁移经验` may become visible resume claims.
- `有知识无实践`, `明确缺口`, and `待确认` remain in private gap, recommendation, and interview-risk artifacts.
- Sparse variants remain explicitly underfilled instead of being padded with unrelated or uncertain material.

Positive wording remains bounded by evidence. The system may select the strongest supported verb and the most favorable truthful ordering, but it never upgrades contribution, broadens a metric, converts a plan into practice, or presents short-term learnability as current evidence.

## Auditable Experience-Duration Near Matches

Experience and skill thresholds are no longer modeled as `ApplicationConstraint`. `ApplicationConstraint` remains limited to independent logistics and eligibility such as location, work authorization, language, travel, schedule, deadlines, and mandatory checks. Experience-, skill-, capability-, and seniority-oriented constraint kinds are rejected.

An unsatisfied hard logistics or eligibility constraint remains blocking and cannot be averaged away by technical evidence.

### Requirement-Side Authority

An explicit atomic numeric duration in a JD is parsed into:

- `Requirement.experience_duration`.

The structure owns:

- one atomic scope;
- unit `years`;
- required minimum;
- optional required maximum.

The structured value must exactly re-parse from the requirement's verbatim quote and source span. Altering an eight-year JD threshold to five years is rejected. Inferred requirements, compound duration expressions, and unsupported free text cannot own a duration threshold.

### Candidate-Side Authority

A candidate duration is accepted only when the current run rebuilds an `EvidenceRecord` from an owning source path, source hash, and exact source span. The extractive safe claim must contain one atomic duration fact plus an explicit checked date, for example:

```text
Maintained 4 years of professional Python development experience; checked 2026-08-30.
```

This creates `EvidenceRecord.experience_duration_fact`, containing:

- atomic scope;
- unit `years`;
- years;
- `checked_at`.

Records without a duration fact, checked date, source hash, or source span cannot support a duration diagnostic.

Each run writes a private metadata-and-fact index:

- `experience-duration-facts.json`.

The index contains evidence IDs, requirement IDs, owning path/section/hash/span, and the parsed duration fact. It does not contain source bodies or snippets.

### User-Facing Binding Entry

Both `generate` and `guided-generate` accept:

```bash
--experience-duration-diagnostics-file /private/path/duration-diagnostics.json
```

The supported workflow is deliberately two-run and non-overwriting:

1. Generate a baseline run.
2. Read `requirements.json`, `evidence-map.json`, and `experience-duration-facts.json`.
3. Create a private binding with the exact requirement ID and an evidence ID from the fact index.
4. Rerun the same target and JD with the diagnostics file.

The rerun reopens owning source spans and rebuilds current evidence records. It verifies that:

- required scope/minimum/maximum equal the requirement-owned structure;
- candidate scope/years/check time equal every referenced record fact;
- every evidence ID exists and is selected by the mapping;
- all scopes are atomic and refer to the same comparison object;
- each requirement receives at most one binding.

Arbitrary selected IDs, self-reported years, missing checked dates, missing source spans, altered JD thresholds, inferred requirements, and compound scopes fail closed.

For an explicit verified shortfall of at most 25%, the recommendation may emit:

```json
{
  "decision": "apply_with_risks",
  "near_match_requirements": ["REQ-..."]
}
```

The rationale retains candidate years, required minimum, shortfall, scope, evidence IDs, checked time, and the explicit statement that the requirement remains unmet and must not be presented as satisfied.

## Application Recommendation and Dossier Output

`ApplicationRecommendation` now carries `near_match_requirements` as a separate auditable dimension.

Generated `role-dossier/gap-analysis.md` now includes an application-recommendation section with:

- decision;

This keeps known limitations visible without turning them into resume claims or silent application blockers.

## Guided Standalone Generation

A new command provides a complete model-free entry point when OMP is unavailable:

```bash
china-targeted-resume guided-generate
```

It can accept either the career repository root or a conventional child such as `company-research`. It:

- normalizes the conventional child to the repository root;
- lists discovered companies and roles;
- accepts a number, exact ID, or exact display value;
- automatically selects a single available option;
- runs dossier, evidence, recommendation, resume, audit, HTML, PDF, preview, and inspection stages.

Interactive choices use a dedicated terminal device. Successful machine output remains one JSON object on stdout. Expected failures remain one JSON object on stderr. EOF and invalid selections do not contaminate the JSON error channel. Non-interactive callers may provide exact `--company` and `--role` values.

Principal implementation areas:

- `src/china_targeted_resume/cli.py`
- `src/china_targeted_resume/pipeline.py`

## Capability-Growth Roadmap Workflow

A separate downstream Skill now owns capability-growth planning:

- `skills/china-resume-growth-roadmap/SKILL.md`

The resume Skill still only analyzes gaps and explicitly exports `roadmap-handoff.json`. A roadmap never becomes current evidence and never changes a match state.

### Strict Roadmap Contract

A new schema defines the final plan:

- `schemas/growth-roadmap.schema.json`.

Each handoff gap must have exactly one plan preserving, without omission or paraphrase:

- `gap_id`;
- `requirement_id`;
- `source_role_refs`;
- `match_state`;
- `severity`;
- `priority_reason`;
- `target_capability`;
- `prerequisite_gap_ids`;
- `baseline_evidence_refs`;
- `suggested_artifacts`;
- `verification_signals`;
- `target_owning_file`.

Each plan requires six ordered stages:

1. `baseline`;
2. `learn`;
3. `practice`;
4. `verify`;
5. `record`;
6. `refresh`.

Every stage includes an objective, prerequisites, work items, expected artifacts, observable pass criteria, effort bounds, and a failure/retry rule.

Each plan also requires at least one HTTPS learning resource with title, publisher, access date, target stage, authority type, and relevance.

### Deterministic Secure Writer

Plugin mode registers `resume_write_growth_roadmap`, a typed tool that routes to the bundled locked Python project through `uv run --project PLUGIN_ROOT --offline --frozen`; it never assumes Plugin installation provides a global CLI. The separately installed standalone surface exposes the same writer as:

```bash
china-targeted-resume write-growth-roadmap \
  --source SOURCE_ROOT \
  --handoff /private/path/roadmap-handoff.json \
  --plan /private/path/draft-growth-roadmap.json \
  --output OUTPUT_ROOT
```

The writer verifies:

- private input ownership and permissions;
- regular-file and non-symlink status;
- a 1 MiB input bound;
- UTF-8 JSON;
- exact handoff SHA-256;
- one plan per handoff gap;
- lossless handoff fields;
- prerequisite references;
- stage order;
- effort bounds;
- HTTPS resources;
- safe relative owning paths;
- the invariant `completion_does_not_change_match_state: true`.

It allocates a new non-overwriting `0700` run directory and atomically writes `0600` artifacts:

```text
growth-roadmap--capability-plan--TIMESTAMP/
├── growth-roadmap.json
├── growth-roadmap.md
└── growth-roadmap.validation.json
```
